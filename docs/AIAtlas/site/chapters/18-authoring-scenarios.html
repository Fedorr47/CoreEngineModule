    18. Авторинг и реальные сценарии: от минимального поведения до полного пути данных¶

    Коротко

    Новое поведение — это согласованный набор: факты и действия (.goap.json), наблюдения и исполнители (.behavior.json), роли уровня (.bindings.json), при необходимости граф маршрутов (.routes.json), запись каталога и development-сценарий для воспроизводимой проверки. Ключевые правила: каждый эффект должен быть наблюдаем, каждый факт — иметь одного writer, радиусы исполнения и наблюдения — быть согласованы. Глава проводит Marker Visit от данных до результата и сводит все текущие сценарии. Статус: SOURCE_VERIFIED.

    1. Задача и интуиция¶

    Предыдущие главы объясняли механизмы по отдельности. Автору поведения нужен порядок работы и проверочный список: что объявить, что с чем должно совпадать, как убедиться, что агент действительно достигает цели, а не «почти». Development-сценарии — способ проверять это через production API на специально построенных уровнях.

    2. Теоретическая выкладка: правила корректного поведения¶

    2.1. Наблюдаемость эффектов¶

    Для каждого действия aaa и каждого эффекта (f,v)∈Ea(f, v) \in E_a(f,v)∈Ea​ должен существовать механизм наблюдения, который после успеха aaa в мире установит f=vf = vf=v. Иначе после успешного шага решение увидит невыполненную цель и будет перепланировать (глава 08). Формально нужен «мост» Of\mathcal O_fOf​: если runtime aaa завершился успешно, то на ближайшем наблюдении Of(мир)=v\mathcal O_f(\text{мир}) = vOf​(мир)=v.

    2.2. Согласованность радиусов¶

    Исполнение и наблюдение часто описывают «одно и то же место» разными числами. Для move_to к роли TTT и within_distance к той же роли:

    (rmove+0.001)2+Δy2⏟худшая точка остановки  ≤  Robs2, \underbrace{(r_{\text{move}} + 0.001)^2 + \Delta y^2}_{\text{худшая точка остановки}} \;\le\; R_{\text{obs}}^2 , худшая точка остановки(rmove​+0.001)2+Δy2​​≤Robs2​,

    где rmover_{\text{move}}rmove​ — acceptance (горизонтальный), Δy\Delta yΔy — разница высот основания агента и узла роли, RobsR_{\text{obs}}Robs​ — радиус наблюдения (3D). Для Access Key: move_to к монете — 0.35, nearest_location — 0.6, монета на 0.35 выше пола: 0.3512+0.352≈0.246≤0.360.351^2 + 0.35^2 \approx 0.246 \le 0.360.3512+0.352≈0.246≤0.36 ✓. Для Marker Visit: r=R=0.8r = R = 0.8r=R=0.8, Δy=0.2\Delta y = 0.2Δy=0.2: 0.8012+0.04≈0.682>0.640.801^2 + 0.04 \approx 0.682 > 0.640.8012+0.04≈0.682>0.64 ✗ (глава 13 §6) INFERRED.

    2.3. Минимальность фактов и конечность пространства¶

    Каждый факт удваивает потенциальное число булевых состояний; каждый неограниченный счётчик делает пространство бесконечным. Факты должны покрывать ровно то, от чего зависит применимость действий и цель (марковость, глава 03), а ресурсы — иметь конечные источники.

    2.4. Сценарий как эксперимент¶

    Сценарий — воспроизводимый эксперимент: setup создаёт нужные сущности и сохраняет baseline, start приводит мир к baseline и вызывает production API, update вносит контролируемые вмешательства, stop прекращает работу, reset восстанавливает всё изменённое (трансформы, видимость, pickup, InteractionPoint, брони, links). Состояние сценария живёт в App; runtime Gameplay не должен содержать полей вида «Maze уже запущен». Сценарий не заменяет тест: он упражняет настоящий путь кода, но результат оценивается человеком (глава 19).

    5. Разобранный пример: новый вариант «дойти до маркера и вернуться»¶

    Учебный пример авторинга только данными PROPOSED (в репозитории его нет; не добавлять в runtime в рамках документации):

    1. Факты: markerPresent, markerReached (latch — «побывал»), atHome.
    2. Цель: returnedAfterVisit = {markerReached: true, atHome: true}.
    3. Действия: move_to/goMarker (pre markerPresent, eff markerReached, cont markerPresent); move_to/goHome (pre markerReached, eff atHome).
    4. Наблюдения: target_available → markerPresent; within_distance (marker, latch) → markerReached; within_distance (home, requireEntity: false) → atHome.
    5. Capabilities: два контекста move_to с ролями home → marker и marker → home; радиусы выбрать по §2.2: при подъёме маркера на 0.2 и R_obs = 0.8 взять acceptance 0.7 (0.7012+0.04=0.531≤0.640.701^2 + 0.04 = 0.531 \le 0.640.7012+0.04=0.531≤0.64).
    6. Bindings: роли home, marker на узлы уровня; запись каталога; сценарий с baseline/reset.

    Почему latch для markerReached: без него после ухода от маркера факт стал бы ложным, и остаток плана (goHome требует markerReached) провалился бы на первом же кадре обратного пути.

    6. Типичные ошибки, границы и проверка¶

    • Ненаблюдаемый эффект → вечное перепланирование после успешного шага.
    • Несогласованные радиусы → см. §2.2; проверяйте неравенство до запуска.
    • Факт без writer или два writer → ошибка сборки.
    • Ветка по имени сценария в runtime → запрещено архитектурой: сценарная специфика живёт в ассетах и App.
    • Сценарий без reset → следующий запуск начинается с изменённого мира.
    • Реальное время в сценарии → temporarilyRemoveTargetAtMidpoint использует steady_clock; на паузе или при медленном кадре длительность в кадрах различается (SC-REMOVE-TARGET).

    Проверки: TestGameplayAIAssetComposition.cpp (14), TestGameplayAIDecision.cpp (5) — наличие SOURCE_VERIFIED; ручные проверки сценариев — глава 19.
