# 20. Ограничения и возможное развитие

!!! abstract "Коротко"
    Сначала — **проверенные** границы текущей реализации (каждая подтверждена кодом и разобрана в своей главе).
    Затем — **предложения** со статусом [[PROP]]: каждое сформулировано как контракт и способ проверки, но не
    является частью кода. Эта глава — единственное место атласа, где допускаются схемы PROPOSED.

## 1. Задача и интуиция

Знать ограничения нужно не для критики, а для проектирования: автор поведения должен понимать, какие гарантии
система **не** даёт, а разработчик движка — какие изменения затронут контракты. Смешивание «как есть» и «как могло
бы быть» — частая ошибка документации; здесь они разделены явно.

## 2. Теоретическая выкладка: классификация ограничений

Ограничения удобно классифицировать по тому, какое свойство контура управления (глава
[01](01-architecture.md)) они затрагивают:

| Свойство | Вопрос | Пример ограничения |
|---|---|---|
| **Полнота модели** | всё ли нужное знание есть в фактах? | роли — снимок позиции |
| **Ограниченность вычислений** | гарантированно ли поиск укладывается в кадр? | нет лимита раскрытий и backoff |
| **Согласованность контрактов** | совпадают ли «прибытие» исполнения и наблюдения? | XZ против 3D |
| **Полнота интеграции** | одинаково ли подключены сервисы во всех входах? | GOAP `move_to` без avoidance |
| **Живучесть** | есть ли выход из застревания? | `physicallyBlocked` без recovery |
| **Координация** | что гарантируется нескольким агентам? | брони не влияют на сбор pickup |

### 2.1. Граница «ограничение или дефект»

Ограничение — сознательное или допустимое свойство, которое следует учитывать (локальность avoidance). Дефект —
расхождение между контрактом и поведением (например, ассеты, где прибытие по контракту исполнения не гарантирует
подтверждения наблюдением). Для документации важно не «исправлять» дефекты описанием желаемого поведения: атлас
фиксирует текущее поведение, а исправления — предмет отдельных задач с тестами.

### 2.2. Стоимость изменения контракта

Каждое ограничение связано с несколькими слоями. Изменение влияет на: (а) типы данных (новые поля контекста, факты),
(б) владение и lifetime (кто держит новый сервис), (в) порядок кадра, (г) ассеты и их валидацию, (д) тесты и
сценарии. Чем больше слоёв, тем важнее последовательность «установить границу → ввести новый путь → перевести
потребителей → удалить старый путь → добавить защиту от регрессии» из `AGENTS.md`.

### 2.3. Критерии оценки предложения

Для оценки предложения полезен простой критерий: изменение должно (1) иметь явный контракт (вход, выход,
владение, ошибки), (2) не нарушать направление зависимостей (ядро GOAP остаётся домен-нейтральным), (3) сохранять
порядок кадра или доказывать эквивалентность (правило `AGENTS.md`), (4) иметь сценарий и тест, подтверждающие
поведение.

## 5. Разобранный пример: предложения как контракты

Все пункты этого раздела — [[PROP]]: не реализованы, приведены для обсуждения.

**П1. Сервисы движения в композиции** (ограничение 4). Добавить в `GameplayAIDecisionCreationContext` невладеющие
указатели `const IGameplayObstacleQuery*`, `GameplaySteeringDebugRegistry*`, `GameplayNavigationDebugRegistry*`,
заполнять их в `StartAIDecision` и передавать из `MoveToCapability::CreateBinding` в уже существующий
9-аргументный конструктор `AIMoveToActionBinding`. Контракт lifetime: сервисы принадлежат `GameplayRuntime`/App и
живут дольше решений. Проверка: сценарий Access Key с препятствием на ребре графа; тест композиции, что binding
получает query.

**П2. Согласование радиусов** (ограничение 7). Проверка при создании instance: для пар `move_to` → роль и
`within_distance` → та же роль выдавать диагностику, если $(r + 0.001)^2 + \Delta y^2 > R^2$ при $\Delta y$ из
позиций ролей. Альтернатива — XZ-режим для `within_distance`. Проверка: юнит-тест композиции на ассетах Marker Visit.

**П3. Ограниченный поиск** (ограничение 1). Параметр `maxExpandedStates` у `FindAIPlan` с результатом
«исчерпан бюджет», отличимым от «плана нет», и backoff повторного поиска в `AIDecisionRuntime` (например,
экспоненциальный по числу неудач до изменения фактов). Хранение пути через индекс родителя вместо копии шагов.
Проверка: тест на синтетическом неограниченном домене.

**П4. Политика застревания** (ограничение 10). Runtime маршрута при `physicallyBlocked` дольше порога
возвращает `Failed` с причиной, решение перепланирует. Проверка: сценарий с непроходимым препятствием.

**П5. Отслеживаемые цели** (ограничение 2). Роль с режимом «живая сущность»: позиция читается из transform на
каждом наблюдении, маршрут перестраивается по порогу смещения.

**П6. Брони в сборе pickup** (ограничение 11). `GameplayPickupSystem` пропускает сбор, если объект забронирован
другим агентом. Влияние на сценарий Reservation нужно проверить отдельно.

## 6. Типичные ошибки, границы и проверка

- **Считать предложение текущим поведением.** Всё в §5 — PROPOSED.
- **Чинить ограничение в «соседнем» слое.** Например, обход стен для GOAP нельзя решать правкой планировщика:
  это интеграция сервисов (П1).
- **Менять порядок кадра ради ограничения 8.** Требует доказательства эквивалентности остального порядка.

пункта 14 (результат сборки [[EV]]).
