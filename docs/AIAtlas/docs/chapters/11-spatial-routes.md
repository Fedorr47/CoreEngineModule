# 11. Пространственные маршруты: GOAP-план против маршрута, графы, NavMesh, route cost

!!! abstract "Коротко"
    План отвечает на вопрос «какие действия», маршрут — «через какие точки». В CoreEngine маршрут
    `GameplayRoute` — ломаная из точек и аннотаций сегментов (N точек ↔ N−1 аннотаций). Он приходит из двух
    источников: **авторского графа** `.routes.json` (Дейкстра по ролям уровня, используется GOAP `move_to`) или
    **NavMesh** Recast/Detour (только прямые запуски, сценарий Maze). Стоимость маршрута может стать стоимостью
    GOAP-действия (`routeCost`), но вычисляется один раз при создании instance. Статус: [[SV]].

## 1. Задача и интуиция

Шаг `move_to/start_to_coin_c` — одно символическое действие, но в мире это путь в несколько метров, возможно с
поворотами, прыжком или дверью. GOAP не должен знать о геометрии, а исполнитель движения — о монетах и ключах.
Маршрут — промежуточное представление: упорядоченные мировые точки плюс пометки, какой сегмент проходится обычным
steering, а какой — специальным исполнителем (traversal).

## 2. Теоретическая выкладка

### 2.1. Два уровня поиска

Получается **иерархическое планирование** в упрощённой форме: верхний уровень (GOAP) ищет в пространстве
символических состояний, нижний (route search) — в пространстве мест. Связь — через стоимость:

$$
c(\texttt{move\_to}/k) = \min_{\text{путь } s_k \to t_k} \sum_{e \in \text{путь}} w(e),
$$

где $s_k$, $t_k$ — узлы-роли контекста $k$, $w(e)$ — стоимость ребра. Важно: это **предвычисление** при создании
instance, а не совместный поиск. Если путь изменится (дверь закроется, агент сдвинется), стоимость в GOAP не
обновится.

### 2.2. Поиск на явном графе: Дейкстра с предшественниками

`FindWeightedGameplayRoute` работает на **явном** ориентированном взвешенном графе $(V, E, w)$ с $w \ge 0$:

1. $\text{dist}[s] = 0$, остальные $\infty$; очередь по $(\text{dist}, \text{порядок вставки})$.
2. Извлекаем вершину с минимальной дистанцией; устаревшие записи пропускаем; при извлечении цели — стоп.
3. Релаксация: если $\text{dist}[u] + w(u,v) < \text{dist}[v]$ — обновить $\text{dist}[v]$, запомнить
   предшественника и ребро.
4. Восстановление пути — проход по предшественникам от цели к старту и разворот.

Отличие от GOAP-поиска главы [05](05-planner.md): здесь вершины заранее известны и пронумерованы, поэтому вместо
копии пути в каждом узле хранится массив предшественников — память $O(|V|)$, время
$O((|V| + |E|)\log|V|)$. Сравнение строгое (`<`): при равной стоимости остаётся первый найденный предшественник.
Особые случаи: старт = цель → маршрут из одной точки, стоимость 0; цель недостижима → `NoRoute`; некорректный
граф (дубликат ID, неконечная позиция, отрицательная стоимость, ребро к несуществующему узлу) → `InvalidGraph`.

Направленность существенна: ребро $A \to B$ не даёт $B \to A$. Стоимость ребра по умолчанию — **3D-длина** между
позициями ролей; явная `cost` заменяет её полностью.

### 2.3. NavMesh: полигоны, коридор, «натянутая нить»

NavMesh (Recast/Detour, M. Mononen) строится из статической геометрии: вокселизация, фильтрация непроходимого
(уклон, высота потолка, ступени), **эрозия** проходимой области на радиус агента и разбиение на выпуклые полигоны.
Эрозия — это сдвиг границы внутрь на $r$ (сумма Минковского с диском): после неё центр агента может стоять в
любой точке полигона, не задевая стен. Поэтому NavMesh **зависит от размеров агента**, и CoreEngine строит
отдельный NavMesh на каждый различный профиль.

Параметры переводятся в клетки консервативно ([[NV-CONFIG]]):

$$
r_{\text{cells}} = \left\lceil \frac{r}{c_s} \right\rceil,\quad
h_{\text{cells}} = \left\lceil \frac{h}{c_h} \right\rceil,\quad
\text{climb}_{\text{cells}} = \left\lfloor \frac{\text{step}}{c_h} \right\rfloor ,
$$

где $c_s$ — размер клетки по горизонтали, $c_h$ — по вертикали. Радиус и высота округляются **вверх** (безопасно:
агент не застрянет), допустимая ступень — **вниз** (безопасно: не потребует подъёма выше возможного).

Запрос пути — три шага Detour ([[NV-FINDPATH]]):

1. `findNearestPoly` в коробке полуразмеров `searchExtents` вокруг старта и цели;
2. `findPath` — A* по графу смежности полигонов → **коридор** полигонов; при недостижимости Detour может вернуть
   частичный коридор до ближайшего полигона;
3. `findStraightPath` — алгоритм «воронки» (string pulling) внутри коридора → угловые точки кратчайшей ломаной.

CoreEngine отбрасывает частичный результат: если последний полигон коридора не совпадает с полигоном цели, это
`NoPath` ([[NV-PARTIAL]]). Переполнение буферов (2048 полигонов/точек) — `BufferTooSmall` ([[NV-LIMITS]]).
Наличие нескольких точек ещё не доказывает достижимость — её доказывает именно проверка последнего полигона.

Узлы `.routes.json` — **имена ролей**, позиции берутся из снимка ролей. Traversal-ребро требует привязки в
`bindings.traversals` (имя, цель, тип `jump`/`door`, handle), зарегистрированного link в
`GameplayTraversalLinkRegistry` и совпадения типа и целевой сущности — иначе ошибка создания instance.

### 4.4. Запрос MoveTo и `sourceRadius`

@@code CP-MOVE-RESOLVE 34

При `sourceRadius > 0` ближайший к агенту (по 3D, строгое `<`) узел графа обязан быть стартом контекста, а
дистанция до него — не больше `sourceRadius`; иначе запрос пуст и шаг падает. При 0 проверка пропускается: Target
Recovery может стартовать с середины пути. Сам маршрут **всегда** начинается со стартового узла: follower не
добавляет сегмент от текущей позиции и сразу целится в `points[1]` (глава [12](12-route-follower.md)).

### 4.5. NavMesh

Геометрия — статические меши уровня в мировых координатах с учётом зеркальных трансформаций
([[NV-GEOM-BUILD]]); bake выполняет `appNavigationCoordinator::Advance`, когда меши загружены
([[AP-NAV-COORD]]): сначала профиль по умолчанию, затем профили всех node-bound персонажей. Новый профиль может
быть построен **синхронно** при `ResolveProfile` с невиданными ранее параметрами ([[NV-PROFILES]]). Debug-overlay
NavMesh рисует геометрию **профиля по умолчанию**.

## 5. Разобранный пример

**Maze** ([[AS-SC-MAZE]]): агент с физическими параметрами $r = 0.35$, цилиндр 1.1 (полная высота
$1.1 + 2\cdot0.35 = 1.8$), ступень 0.35, уклон 45°. Bake по умолчанию: $c_s = 0.2$, $c_h = 0.1$
([[NV-BUILD-SETTINGS]]). Клетки профиля агента: радиус $\lceil 0.35/0.2 \rceil = \lceil 1.75 \rceil = 2$ (эрозия
0.4 м), высота $\lceil 1.8/0.1 \rceil = 18$, ступень $\lfloor 0.35/0.1 \rfloor = 3$ (0.3 м — меньше физических
0.35). Профиль по умолчанию ($r = 0.4$, ступень 0.4): радиус $\lceil 2.0 \rceil = 2$ (та же эрозия), ступень
$\lfloor 4.0 \rfloor = 4$. Значит, overlay по умолчанию может показывать проходимой ступень 0.4 м, которую
профиль агента не допускает. Запрос: `searchExtents (1, 2, 1)` — коробка ±1 м по X/Z и ±2 м по Y; результат —
точки straight path, маршрут без аннотаций, acceptance 0.25, slowing 0.9, ходьба.

**Access Key, `sourceRadius`**. Шаг `access_key_shop_to_goal` стартует, когда агент у магазина
`(0, 0.35, −7)`. Ближайший узел графа — `shop`; если агент стоит в 0.3 м от него, $0.3 \le 0.6$ → запрос
разрешён, маршрут `shop → goal` из двух точек стоимостью 17.0021 (прямое ребро). Если же агента оттолкнули так, что
ближе оказался `coinA`, запрос пуст → шаг `Failed` → решение перепланирует из наблюдаемого состояния
(глава [08](08-decision-runtime.md)).

## 6. Типичные ошибки, границы и проверка

- **Ждать обхода стен от GOAP `move_to` без графа.** Прямой fallback — отрезок между ролями; NavMesh не
  используется ([[CP-MOVE-FALLBACK]]).
- **Обратное ребро.** Граф ориентированный; путь назад требует своего ребра.
- **Устаревший route cost.** Стоимость фиксируется при создании instance.
- **Частичный коридор.** Не путь; CoreEngine корректно возвращает `NoPath`.
- **Другой профиль в overlay.** Проверяйте параметры профиля агента, а не картинку default-NavMesh.
- **Синхронный bake.** Новый профиль строится в момент запроса — возможна заметная пауза кадра [[INF]].
