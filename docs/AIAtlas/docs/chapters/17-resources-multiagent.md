# 17. Ресурсы и несколько агентов: ledger, покупка, брони и конкуренция

!!! abstract "Коротко"
    Ресурсы в CoreEngine — целочисленные факты, которые меняет только наблюдение `resource_ledger` по подтверждённым
    событиям (`PickupCollected`, `ResourcePurchased` с `receiptId`). Покупка — мгновенное действие, которое лишь
    **создаёт событие**; списание делает ledger в том же update. Модель покупки в GOAP обязана совпадать с
    исполнением — это проверяется при сборке. Несколько агентов разделяют мир, но не факты; координация — только
    через брони Interaction Point, которые действуют на старте шагов `move_to` и на наблюдение доступности, но
    **не** на систему сбора pickup. Статус: [[SV]]; разбор конкуренции — [[INF]].

## 1. Задача и интуиция

Как только у агента появляется ресурс (монеты) и способ его потратить (покупка), возникают вопросы учёта: кто
начисляет, как не начислить дважды, как гарантировать, что планировщик и мир «считают» одинаково. С несколькими
агентами добавляется конкуренция: два агента планируют забрать одну и ту же монету. Глава описывает, что CoreEngine
гарантирует и чего — нет.

## 2. Теоретическая выкладка

### 2.1. Бухгалтерия как журнал событий

Баланс — свёртка подтверждённых событий агента:

$$
\text{coins} = \sum_{p \in \text{pickups}} a_p\,[\text{collected}_p] - \sum_{q \in \text{receipts}} \text{price}_q\,[\text{bought}_q].
$$

Ledger поддерживает её инкрементально, с двумя свойствами:

- **идемпотентность**: событие о предмете $p$ учитывается, только если `collected_p` ещё ложно; повтор не
  начисляет; аналогично для receipt — результат ещё не подтверждён;
- **атомарность записи**: сумма считается в 64-битном типе, и при выходе за int32 кредит отбрасывается целиком,
  без частичной установки `collected_p` ([[CP-LEDGER-OBSERVE]]).

`receiptId` различает несколько результатов у одного продавца: событие покупки сопоставляется по паре
(subject, receiptId), а не только по продавцу.

### 2.2. Согласованность модели и исполнения

Планировщик рассуждает по модели действия; мир — по runtime и ledger. Чтобы «покупка в плане» и «покупка в мире»
совпадали, `PurchaseCapability` при сборке проверяет для каждого контекста ([[CP-PURCHASE-CAP]]):

$$
E^{\text{bool}}_a = \{(\text{result}_q, 1)\}, \quad
E^{\text{int}}_a = \{(\text{coins}, \text{add}, -\text{price}_q)\}, \quad
(\text{coins} \ge \text{price}_q) \in P^{\text{int}}_a .
$$

Если автор напишет в определении `add -1` при цене 2, сборка упадёт с «purchase definition effects do not match
the receipt/price», а не начнёт «покупать в долг» в плане.

### 2.3. Брони как взаимное исключение

`GameplayObjectReservationSystem` хранит владельца для объекта (`objectEntity → agentEntity`). Это
**необязательная блокировка** (advisory lock): она действует только там, где её проверяют:

| Где проверяется | Эффект |
|---|---|
| `ReservedAIMoveToActionRuntime::Start` | шаг к цели с бронью стартует, только если цель никем не занята; затем бронирует ([[NA-RESERVED-START]]) |
| `ReservedAIMoveToActionRuntime::Tick` | потеря брони → отмена движения, `Failed` |
| `pickup_available` с `respectReservations` | чужая бронь → предмет «недоступен» в фактах |
| `DoorTraversalExecutor` | дверь резервируется на время прохода |
| `GameplayPickupSystem` | **не проверяется**: собирает любой AI-агент в радиусе ([[PK-SYSTEM]]) |

Отсюда класс гонок *time-of-check/time-of-use*: план строится по фактам момента $t$, а бронь берётся при старте
шага в $t' > t$. Между ними другой агент может забронировать цель; тогда старт шага неуспешен, а следующее
наблюдение уже видит бронь и перепланирует. Планировщик **не бронирует будущие шаги**: брони — часть контракта
исполнения, а не планирования.

### 2.4. Ограничения гарантий

- Нет справедливости: при равных условиях выигрывает агент, обновляемый раньше (меньший `EntityHandle`).
- Нет глобальной координации: агенты не договариваются о распределении ресурсов; задача «каждому нужно 2, всего 3»
  решается тем, что один агент остаётся в `Failed`.
- Бронь не защищает от сбора: агент, проходящий в радиусе чужой брони, всё равно соберёт pickup.

## 5. Разобранный пример

**Покупка ключа** (Access Key): у магазина `coins = 2`, `hasAccessKey = 0`, агент в 0.3 м от узла
`GOAP_Access_Key (0, 0.35, −7)` (3D-дистанция с учётом высоты $\sqrt{0.3^2 + 0.35^2} \approx 0.46 \le 0.6$).
`PurchaseRuntime::Start` → `ResourcePurchased(agent, shop, "unlock")` → `Succeeded`. Второй проход ledger:
`coins 2 → 0`, `hasAccessKey 0 → 1`. Реакция: `HideEntityRequested(agent, shop)` → узел скрыт. Повторное событие
с тем же receipt не изменит факты (результат уже подтверждён). Обратите внимание: скрытие не удаляет сущность,
поэтому другой агент со своими монетами может купить свой ключ у того же продавца.

**Два агента** ([[AS-SC-RESERVATION]]): агенты стоят у `GOAP_Start` на $x = \pm0.45$ (оба в `sourceRadius` 0.6
от узла старта), решение `access_key_reserved` (все движения к монетам с `reserveTarget`, все `pickup_available` с
`respectReservations`). Оба первых update строят один и тот же план C → A → магазин (42.09). Дальше по коду
[[INF]]:

1. В `PrePhysicsUpdate` первым обновляется агент с меньшим handle — назовём его A: шаг `start_to_coin_c`
   бронирует монету C.
2. Агент B пытается стартовать тот же шаг: `IsReserved(coinC)` → старт неуспешен → план `Failed`.
3. Следующий update B: `coinCAvailable = 0` (чужая бронь) → новый план B → A → магазин:
   $6.0912 + 12.6491 + 7.2111 + 1 + 17.0021 = 43.95$.
4. Оба идут шагом (2 м/с): B доходит до монеты B (6.09 м) раньше, чем A — до C (7.82 м), и бронирует монету A.
5. A у монеты C пытается стартовать `coin_c_to_coin_a`: монета A занята → неуспех; при перепланировании
   `coinAAvailable = 0` (бронь B), `coinBAvailable = 0` (собрана) → плана нет, A остаётся в `Failed`.
6. B собирает A, покупает ключ и доходит до цели. A навсегда без второй монеты.

Итог определяется ресурсом (3 монеты на двоих при потребности 2 на агента), порядком handles и скоростями — в
приложении не наблюдался [[NV]].

## 6. Типичные ошибки, границы и проверка

- **Считать бронь исключительным правом на сбор.** Pickup system бронь игнорирует.
- **Ожидать, что план «зарезервирует» будущие шаги.** Бронь берётся при старте шага.
- **Собственная бронь при повторном старте.** `ReservedAIMoveToActionRuntime::Start` отклоняет и **свою**
  существующую бронь (`IsReserved` без учёта владельца) [[SV]].
- **Несогласованная модель покупки.** Ловится сборкой; не обходите проверку собственным runtime.
- **Порядок агентов.** Детерминирован по handle; не является политикой распределения.
