# 04. Цели и контракты действий: выбор цели, применимость, продолжение, стоимость

!!! abstract "Коротко"
    Цель — набор требуемых булевых фактов с оценкой; выбирается неудовлетворённая цель с наибольшей оценкой
    (при равенстве — первая по порядку). Действие несёт **три разных контракта**: предусловия (можно ли начать),
    эффекты (что модель ожидает после успеха) и условия продолжения (что обязано оставаться истинным, пока шаг
    выполняется). Стоимость — единственный критерий выбора между планами. Статус: [[SV]].

## 1. Задача и интуиция

Глава [02](02-goap-strips.md) описала действие как пару «предусловия — эффекты». Для игры этого мало по двум
причинам. Во-первых, целей обычно несколько, и нужно выбрать, над какой работать сейчас. Во-вторых, действие в игре
**длится**: агент бежит к маркеру несколько секунд, и за это время мир меняется. Нужно различать «можно ли начать»
и «можно ли продолжать», иначе либо действие прерывается без причины, либо продолжается, когда смысла уже нет.

## 2. Теоретическая выкладка

### 2.1. Выбор цели как argmax с фильтром

Пусть цели $G_1, \dots, G_m$ заданы в порядке определения, у каждой — базовая оценка $b_k$, требуемые факты
$D_k$ и (опционально) правила $(c_{kj}, \delta_{kj})$: «если условие $c_{kj}$ истинно, прибавить $\delta_{kj}$».
Оценка в состоянии $S$:

$$
\operatorname{score}_k(S) = b_k + \sum_j \delta_{kj}\,[\,c_{kj}(S)\,],
$$

где $[\cdot]$ — индикатор (1, если истинно). Кандидаты — цели, **ещё не выполненные** в $S$
($\neg D_k(S)$) и с конечными значениями. Выбор:

$$
k^{\ast} = \min\{\,k : \operatorname{score}_k = \max_j \operatorname{score}_j\,\},
$$

то есть максимум оценки, а при равенстве — **первая** по порядку цель (строгое сравнение `score > best`,
[[GS-TIE]]). Если кандидатов нет, «нет цели» — решение считает работу выполненной.

Это не полноценная функция полезности: правила аддитивны, зависят только от булевых фактов и не учитывают
стоимость плана. Связи «выбор цели ↔ стоимость плана» нет: если для выбранной цели плана не существует, менее
приоритетные цели **не перебираются** автоматически [[SV]].

### 2.2. Три контракта действия

Аналогия из планирования с длительными действиями (PDDL 2.1, M. Fox и D. Long, 2003): у durative action есть
условия *at start*, *over all* и эффекты *at end*. В CoreEngine:

| Контракт | PDDL-аналог | Где проверяется | Смысл |
|---|---|---|---|
| preconditions $P_a$ | at start | поиск; перед стартом шага — весь остаток плана | можно начать |
| continuationConditions $C_a$ | over all | каждый update, пока шаг `RunningStep` | основание сохраняется |
| effects $E_a$ | at end | только прогноз (поиск, остаток плана) | что ожидаем после успеха |

**Правило подмножества.** CoreEngine требует $C_a \subseteq P_a$: каждое условие продолжения должно буквально
совпадать с одним из предусловий (для числовых — тот же факт, оператор и значение, [[PL-CONT-SUBSET]]). Зачем:

1. продолжение гарантированно истинно в момент старта (иначе шаг мог бы инвалидироваться сразу после запуска);
2. автор явно выбирает, какие стартовые основания являются **поддерживаемыми** («цель доступна»), а какие —
   **расходуемыми** («монет ≥ 2», которые покупка сама потратит).

Почему не проверять все предусловия всё время? Потому что действие может само менять своё основание. Покупка
требует `coins ≥ 2` и сама списывает 2; агент, бегущий к монете, перестаёт быть `atStart`. Повторная проверка всех
$P_a$ каждый кадр прерывала бы корректное исполнение.

Формально: шаг $a$, запущенный в момент $t_0$, продолжается в $t > t_0$, пока $C_a(O_t)$ истинно, где $O_t$ —
наблюдаемые факты. В поиске $C_a$ не используется: на входе в действие оно покрыто $P_a$.

### 2.3. Стоимость

Стоимость $c(a) \ge 0$ — единица выбора между планами. Смысл единиц задаёт автор: секунды, метры или условные
«усилия» — но **согласованно** для всех действий, которые могут конкурировать. В Access Key стоимости движения
заменены длинами путей (метры), а покупка стоит 1 — значит, покупка эквивалентна метру пути; это авторское решение,
и его стоит осознавать, когда добавляются альтернативные способы получить ключ.

## 4. Как это реализовано в CoreEngine

### 4.1. Выбор цели

@@code GS-SCORE 56

Важно для авторов ассетов: компилятор `.goap.json` создаёт кандидата только с `baseScore = score`, правила
`scoreRules` остаются пустыми ([[AU-GOAL-BUILD]]). Значит, в ассетной композиции выбор цели — это «наибольший
`score` среди невыполненных, при равенстве — первый в файле». Правила доступны только программному коду, который
сам строит `AIGoalSelectionCandidate` ([[GS-CANDIDATE]]).

### 4.2. Контракт продолжения в runtime

@@code DR-CONTINUATION 26

Шаг ищется по паре `(actionId, contextId)`; если определения нет — продолжение считается нарушенным.

### 4.3. Проверка остатка плана перед стартом шага

@@code DR-REMAINING 38

Это «мини-поиск без ветвления»: остаток плана прогоняется по **текущим фактам** с применением эффектов к копии, и в
конце проверяется цель. Если предыдущий шаг удался, но наблюдение ещё не подтвердило его эффект, проверка не пройдёт
и решение будет перепланировать (глава [08](08-decision-runtime.md)).

### 4.4. Где проверяется правило подмножества

Компилятор определения и template правило $C_a \subseteq P_a$ **не проверяют**; его проверяет `IsInputValid`
планировщика ([[PL-INPUT]]). Нарушение даёт `nullopt` при каждом поиске [[INF]] (см. главу
[05](05-planner.md) §4.1).

## 5. Разобранный пример

**Marker Visit** ([[AS-MARKER-GOAP]]). Действие `move_to/visitMarker`: $P = \{$`markerPresent = true`$\}$,
$E = \{$`markerReached = true`$\}$, $C = \{$`markerPresent = true`$\}$ ⊆ $P$ ✓, стоимость 2. Пока агент бежит,
маркер должен оставаться доступным; если его InteractionPoint исчезнет, шаг будет прерван.

**Access Key** ([[AS-ACCESS-BUY]]). У `purchase/buy_key` $P = \{$`hasAccessKey = false`, `atAccessKeyShop = true`,
`coins ≥ 2`$\}$, $E = \{$`hasAccessKey = true`, `coins += −2`$\}$, $C = \varnothing$. Продолжения нет: покупка
мгновенна (`Start` сразу возвращает `Succeeded`, глава [17](17-resources-multiagent.md)), а основание `coins ≥ 2` —
расходуемое.

**Выбор цели (учебный пример).** Две цели в порядке определения: `patrol` ($b = 1$) и `flee` ($b = 1$) с
правилом `threatSeen = true → +5`. При `threatSeen = false`: оценки $1$ и $1$ → выбирается `patrol` (первая при
равенстве). При `threatSeen = true`: $1$ и $6$ → `flee`. Если `flee` уже выполнена (`safe = true` — её
`desiredFacts`), она исключается до оценки, и выбор возвращается к `patrol`. Такое правило нельзя записать в
`.goap.json` — только кодом.

## 6. Типичные ошибки, границы и проверка

- **Ожидать перебора целей.** Если для выбранной цели плана нет, решение `Failed`, другая цель не пробуется.
- **Равные score.** Порядок целей в файле — часть поведения.
- **Continuation вне preconditions.** Нет ошибки загрузки, но планов не будет никогда.
- **Расходуемое основание в continuation.** Шаг прервёт сам себя, как только начнёт достигать цели.
- **Эффект, который нельзя наблюдать.** Цель будет «вечно» перепланироваться после успешного шага.
- **Несогласованные единицы стоимости.** Оптимальный по числу план окажется не тем, что ожидал автор.
