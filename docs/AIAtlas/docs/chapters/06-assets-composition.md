# 06. Ассеты и композиция: catalog, behavior, bindings, template и instance

!!! abstract "Коротко"
    Поведение собирается из **нескольких файлов с разной ответственностью** и **зарегистрированных компонентов**.
    Сборка идёт в две стадии: при регистрации каталога всё, что не зависит от уровня и агента, разбирается,
    компилируется и проверяется в неизменяемый `GameplayGOAPDecisionTemplate`; при старте решения template
    связывается с уровнем (роли — снимок позиций и сущностей) и порождает instance со своими фактами,
    наблюдениями, провайдерами и bindings. Регистрация каталога транзакционна. Статус: [[SV]].

## 1. Задача и интуиция

Если бы каждое поведение было классом C++, новое поведение требовало бы программиста и пересборки, а сценарная
специфика проникала бы в общий runtime. CoreEngine разделяет: **что знает агент и что он умеет** (GOAP-определение),
**как факты вычисляются и как шаги исполняются** (компоненты), **где это происходит на уровне** (bindings ролей).
Новый вариант поведения часто сводится к новому набору JSON; новый **тип** наблюдения или исполнителя — к одному
C++-компоненту с регистрацией, без правки общей композиции.

## 2. Теоретическая выкладка

### 2.1. Конвейер «разбор → компиляция → связывание»

Сборка — это компилятор маленького языка поведения:

1. **Разбор** (parse): JSON → типизированные структуры; ошибки формата (неизвестное поле, неверный тип,
   версия ≠ 1).
2. **Компиляция** (compile): имена → идентификаторы, проверка символов, типов фактов, уникальности; результат
   не зависит от уровня.
3. **Связывание** (link): имена ролей → узлы конкретного уровня и сущности; создание объектов, хранящих состояние.

Принцип — **проверять как можно раньше то, что можно проверить**: всё, что зависит только от ассетов, проверяется
при регистрации каталога (один раз на запуск), а зависимое от уровня — при создании instance. Ошибка второго рода
не может быть обнаружена раньше: тот же behavior может быть корректен на одном уровне и некорректен на другом.

### 2.2. Расширяемость через реестр (open/closed)

Реестр компонентов хранит для каждого типа пару функций: **parser** (`JSON → T`) и **compiler**
(`T + контекст → объект`). Поскольку типы параметров различны, контейнер хранит их как `std::any`, а компилятор
извлекает ожидаемый тип `Parameters<T>` с проверкой. Это классический приём «открыт для расширения, закрыт для
изменения»: добавление компонента не меняет общий код композиции и не требует закрытого `std::variant` со всеми
встроенными типами. Цена — проверка типа в рантайме (ошибка «incorrect typed parameters», если parser и compiler
несогласованы).

`std::any` существует только на стадии авторинга. Рабочее состояние GOAP — по-прежнему фиксированный вектор
bool/int (глава [03](03-state-model.md)).

### 2.3. Неизменяемый template и состояние на агента

Template — **неизменяемый снимок** (`shared_ptr<const ...>`): все агенты одного решения разделяют разобранные
ассеты и скомпилированное определение. Всё изменяемое — факты, память latch, позиция route follower, флаги
реакций, буферы событий — создаётся заново для каждого instance. Это шаблон *flyweight*: разделяется
тяжёлое и неизменное, дублируется лёгкое и изменяемое. Следствие: прогресс одного агента не может «протечь» в
другого, а пересоздание каталога не затрагивает уже работающие instance (они держат свой `shared_ptr`).

### 2.4. Транзакционная публикация

Регистрация каталога работает по схеме *copy → modify → swap*: строится копия реестра фабрик, в неё добавляются все
записи, и только после успеха всех записей копия заменяет оригинал. Свойство «всё или ничего»: ошибка в последнем
behavior не оставляет половину каталога зарегистрированной. Формально, если $R$ — реестр до вызова, а $E_i$ —
успех $i$-й записи, то результат

$$
R' =
\begin{cases}
R \cup \{f_1, \dots, f_n\}, & \bigwedge_i E_i,\\
R \;(\text{и исключение}), & \text{иначе}.
\end{cases}
$$

### 2.5. Раннее связывание ролей

Роль связывается **один раз** при создании instance: позиция берётся из `LevelAsset.nodes[i].transform.position`,
сущность — из единственной gameplay-сущности с `NodeLink` на этот узел. Это *раннее связывание*: дешёвое и
детерминированное, но не отслеживающее движение. Если цель переедет, наблюдения и маршруты будут работать с
исходной позицией; если сущность пересоздадут с новым handle, роль останется привязанной к старому. Для
подвижных целей предназначены отдельные runtimes FollowTarget/FleeTarget (глава [14](14-temporal-behaviors.md)).

## 4. Как это реализовано в CoreEngine

### 4.1. Файлы и их проверки

| Файл | Тип C++ | Проверки разбора |
|---|---|---|
| `catalog.json` | `GameplayAIDecisionCatalogAsset` | `version == 1`, поля `id/behavior/bindings`, уникальные ID |
| `*.behavior.json` | `GameplayAIBehaviorAsset` | `version`, известные поля, parser каждого компонента, уникальный `context` capability ([[AU-BEHAVIOR-PARSE]]) |
| `*.goap.json` | `GameplayGOAPDefinitionAsset` | обязательные поля и типы; **без** проверки версии и лишних полей ([[AU-GOAP-PARSE]]) |
| `*.bindings.json` | `GameplayAILevelBindingsAsset` | `version`, роли уникальны, traversal: имя, цель, тип, handle > 0 |
| `*.routes.json` | `GameplayAIRouteGraphAsset` | `version`, `nodes`, рёбра `from/to/[traversal]/[cost ≥ 0]` ([[AU-ROUTES-PARSE]]) |

Общие помощники разбора — `Root` (версия 1) и `Fields` (запрет неизвестных полей): [[AU-ROOT]], [[AU-FIELDS]].

### 4.2. Реестр компонентов

@@code CO-REG-CAP 27

Встроенные регистрации ([[CO-BUILTIN]]): наблюдения `target_available`, `within_distance`, `nearest_location`,
`pickup_available`, `resource_ledger`; capabilities `move_to` (`AIActionId 2`) и `purchase` (`AIActionId 3`);
реакция `hide_on_purchase`. **Имя типа capability совпадает с именем семантического действия** в `.goap.json`
([[CO-SEMANTIC]]): строка `"action": "move_to"` в определении компилируется в `AIActionId 2` именно потому, что
зарегистрирована capability `move_to`.

### 4.3. Template

@@code CO-TEMPLATE 64

Проверки конструктора: `model == "goap"`; если указан `routeGraph`, граф загружен; определение компилируется с
семантическими действиями реестра; известны типы наблюдений и реакций; у каждого контекста определения ровно одна
capability, и её тип совпадает с `action` этого контекста. `InstanceDefinition` копирует определение и применяет
стоимости провайдеров (конечные, неотрицательные, без повторов, только для существующих пар) ([[CO-INSTANCE-DEF]]).

### 4.4. Регистрация каталога

@@code CO-REGISTER-ASSETS 59

Детали: загрузка и построение template обёрнуты в `try`, и ошибка переупаковывается с префиксом
`Decision '<id>' (behavior '…', bindings '…'): `; фабрика при вызове ловит исключения создания instance и
возвращает `nullptr` с диагностикой ([[CO-PENDING]]).

### 4.5. Создание instance

@@code CO-RESOLVE-ROLES 52

Ошибки связывания: дубликат роли, отсутствующий или неоднозначный узел (два живых узла с одним именем),
неконечная позиция, несколько gameplay-сущностей на один узел. Роль без сущности допустима — проверку наличия
сущности делает компонент, которому она нужна (например, `target_available` с `requireEntity` по умолчанию).

Далее `CreateGameplayGOAPDecisionFromTemplate` ([[CO-FROM-TEMPLATE]]) компилирует наблюдения, упорядочивает их
(глава [07](07-observations-events.md)), компилирует реакции и capability-группы, собирает cost overrides и
вызывает `CreateGameplayGOAPDecision` ([[GG-CREATE]]). Если `inspectPath: true`, контекст получает реализацию
`IGameplayGOAPPlannedPathProvider` и instance — интерфейс отладки планируемого пути.

## 5. Разобранный пример: сборка Access Key

1. **Каталог** ([[AS-CATALOG]]) содержит 5 решений; `access_key` и `access_key_reserved` используют **одни и те же
   bindings** — разные поведения на одном уровне.
2. **Компиляция определения**: 14 bool + 1 int факт; 1 цель `reachDestination` (score 1); 14 действий →
   контексты `0..13` в порядке файла (13 `move_to` и `buy_key`); семантические ID из реестра: `move_to → 2`,
   `purchase → 3`.
3. **Template**: capability-группы `move_to` (13 ассетов) и `purchase` (1); каждый контекст покрыт ровно одной
   capability; граф маршрутов загружен (`routeGraph`).
4. **Создание instance на уровне** `ai_goap_access_key_development`: роли `start → GOAP_Start (0, 0.03, 0)`,
   `coinA → GOAP_Coin_A (−6, 0.35, −3)` и т.д. (позиции — снимок узлов уровня).
5. **Наблюдения в авторском порядке**: `resource_ledger` (выходы: `coins`, `coin*Collected`, `hasAccessKey`),
   три `pickup_available`, `nearest_location` (шесть `at*`), `within_distance` (вход `hasAccessKey`, выход
   `atDestination`). Вход последнего производит ledger, который стоит раньше, — порядок сохраняется. Если бы автор
   поставил `within_distance` первым, упорядочивание переставило бы его после ledger.
6. **Capabilities**: `MoveToCapability` компилирует граф маршрутов (роли → узлы), для каждого контекста считает
   кратчайший путь и, так как `routeCost: true`, возвращает 13 cost overrides (стоимости — в главе
   [05](05-planner.md)); `PurchaseCapability` проверяет модель покупки (глава [17](17-resources-multiagent.md)).
7. **InstanceDefinition** — копия определения, где у 13 действий `move_to` стоимость 1 заменена длинами путей.
8. **Instance**: реакция `hide_on_purchase`, bindings двух семантических действий, `inspectPath: true` →
   доступен планируемый путь в отладке.

Типичная диагностика при ошибке автора (тексты из кода):

| Ошибка | Сообщение |
|---|---|
| контекст без capability | `action context '<ctx>' has no capability binding` |
| capability не совпадает с действием | `capability does not match a definition action/context '<ctx>'` |
| роль без узла | `role '<role>': missing node '<node>'` |
| факт без writer | `fact has no observation writer` |
| `routeCost` без графа | `routeCost requires an authored route graph` |

## 6. Типичные ошибки, границы и проверка

- **Ожидать hot reload.** Изменения ассетов требуют пересоздания реестра фабрик (в App — пересоздание
  `GameplayRuntime`); живые instance сохраняют старую конфигурацию.
- **Опечатки в `.goap.json`.** Лишние поля здесь не запрещены (в отличие от behavior/bindings/routes) — опечатка в
  необязательном поле (`continuationCondition` вместо `continuationConditions`) будет тихо проигнорирована [[INF]].
- **Роль как трекер.** Роль — снимок; перемещение или пересоздание цели не отслеживается.
- **Неоднозначные узлы.** Два живых узла с одним именем — ошибка создания, а не «первый найденный».
- **Пустой каталог.** `GameplayRuntime()` без фабрик ничего не знает о каталоге ([[GR-CTOR]]).
