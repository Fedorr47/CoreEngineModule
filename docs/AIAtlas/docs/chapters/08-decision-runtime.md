# 08. Decision runtime: мониторинг плана, перепланирование, Failed и Cancel

!!! abstract "Коротко"
    `AIDecisionRuntime` — исполнитель одного агента: синхронизирует текущий шаг с `AISystem`, выбирает цель,
    проверяет план (остаток плана перед стартом шага, continuation во время шага), ищет новый план **до** отмены
    старого и запускает шаги по одному. `Failed` — нормальное состояние живого решения, из которого оно может
    восстановиться; явный `Cancel` останавливает автоматическое продолжение; удаление instance из
    `GameplayRuntime` — конец решения. Статус: [[SV]], пример по кадрам — [[INF]] (выведен из кода и сценария).

## 1. Задача и интуиция

Глава [05](05-planner.md) находит план для заданного состояния. Но состояние меняется каждый кадр. Нужен контур,
который отвечает на вопросы: когда искать заново? можно ли продолжать текущий шаг? что делать, если нового плана
нет? как отличить «временно не получается» от «прекратить»? Эту роль играет `AIDecisionRuntime`; обёртки
`GameplayGOAPDecision` и `GameplayGOAPDecisionInstance` добавляют к нему факты, наблюдения и события
(глава [07](07-observations-events.md)).

## 2. Теоретическая выкладка

### 2.1. Машина состояний исполнения плана

`AIPlanExecution` — конечный автомат над индексом текущего шага $i$:

| Состояние | Смысл | Выход |
|---|---|---|
| `NotStarted` | план создан | `Start()`: пустой → `Succeeded`, иначе `ReadyToStartStep` |
| `ReadyToStartStep` | шаг $i$ готов, runtime ещё не создан | старт удался → `RunningStep`; нет → `Failed` |
| `RunningStep` | runtime шага $i$ работает в `AISystem` | `Succeeded` → $i{+}{+}$ и Ready или план `Succeeded`; `Failed`/`Cancelled` |
| `Succeeded`, `Failed`, `Cancelled` | terminal | — |

Мгновенное действие (покупка) проходит `Ready → Running → Ready(i+1)` в одном вызове моста
(`StartReadyPlanStep` применяет `Succeeded` сразу).

### 2.2. Решение как таблица условий

Обозначим: $g$ — выбранная цель, $g_{\text{prev}}$ — цель исполняемого плана, $E$ — исполнение (может
отсутствовать), $O$ — наблюдаемые факты. Инвалидация определена **только при неизменной цели**:

$$
\text{inv} = [g = g_{\text{prev}}] \wedge \Big( \big[E = \text{Ready}\big] \wedge \neg V_{\text{rest}}(E, O)
\;\vee\; \big[E = \text{Running}\big] \wedge \neg C_{a_i}(O) \Big),
$$

где $V_{\text{rest}}$ — прогон остатка плана по $O$ с проверкой цели, $C_{a_i}$ — условия продолжения текущего
шага. Дальше:

| Цель | inv | Исполнение | Действие |
|---|---|---|---|
| нет цели | — | любое | отменить, `Succeeded` |
| прежняя | нет | нетерминальное | продолжать (старт Ready-шага или sync) |
| прежняя | да | — | поиск; найден → установить; нет → отменить, `Failed` |
| прежняя | — | отсутствует или terminal | поиск; найден → установить; нет → `Failed` |
| новая | — | нетерминальное | поиск; найден → установить; **нет → сохранить старое** |
| новая | — | отсутствует или terminal | поиск; найден → установить; нет → `Failed` |

Исключение: в том update, где синхронизация показала, что план **только что** выполнен целиком, а цель прежняя
(наблюдение ещё не подтвердило её), возвращается `Succeeded` без поиска; поиск по «прежняя цель, terminal»
произойдёт в следующем update ([[DR-UPDATE]]).

Принцип **make-before-break**: новый план ищется, пока старое исполнение ещё живо; отмена происходит только при
установке замены (`InstallPlan_`) или когда замены нет и старое уже невалидно. Это предотвращает «пустые» кадры при
успешном перепланировании.

Особая строка — «новая цель, плана нет»: старое исполнение сохраняется, хотя оно служит **прежней** цели, и его
continuation на этой ветви не перепроверяется. `selectedGoalId_` тоже остаётся прежним, поэтому на следующем
update цель снова будет «новой», и поиск повторится. Утверждать «при неуспешной смене цели старый план всегда
перепроверен» было бы неверно [[SV]].

### 2.3. Почему после успешного шага нужен ещё update

Когда задача шага возвращает `Succeeded`, решение узнаёт об этом в начале своего следующего update (sync). В этом
же update оно проверяет остаток плана по **новым** фактам, но не стартует следующий шаг (ветвь «был sync» →
возврат). Шаг стартует на следующем update. Это даёт наблюдениям кадр, чтобы подтвердить эффекты завершённого шага
(например, сбор монеты происходит в `pickupSystem_.Update` уже после завершения движения) [[INF]].

### 2.4. Жизнеспособность: повторный поиск без backoff

Решение в `Failed` без исполнения на каждом update выполняет `FindAIPlan`. Если пространство состояний мало, это
дёшево; гарантии, что поиск завершится, дают только авторские ограничения (глава [05](05-planner.md) §2.2).
Backoff и бюджета нет.

### 2.5. Три способа «остановиться»

| Механизм | Что происходит | Возобновится само? |
|---|---|---|
| `Failed` (нет плана, шаг упал) | исполнение отменено/отсутствует; instance жив и наблюдает | да, когда наблюдение позволит найти план |
| `AIDecisionRuntime::Cancel` | `bExplicitlyCancelled_ = true`, отмена исполнения | нет; флаг снимает только успешный `Plan(...)` |
| `GameplayRuntime::CancelAIDecision(entity)` | `Cancel` + удаление instance | нет; новый старт создаёт новый instance |

`Cancelled` ([[SC-RUNNER-UPDATE]]).

## 5. Разобранный пример: Target Recovery по кадрам

Данные: behavior ([[AS-RECOVERY-BEHAVIOR]]) — `target_available` (InteractionPoint) → `goalAvailable`,
`within_distance` 0.4 → `atDestination`; `move_to` из `origin` в `destination`, acceptance 0.4, slowing 1.5,
ходьба. Уровень: старт `(−10, 0, 0)`, цель `(10, 0.2, 0)`. Сценарий ([[AS-SC-RECOVERY]]):
`temporarilyRemoveTargetAtMidpoint`, `distanceFraction` 0.5, `unavailableSeconds` 5.0.

1. **Старт.** Факты: `goalAvailable = 1`, `atDestination = 0`. План `[move_to/destination]` (стоимость 1) →
   `ReadyToStartStep`; instance сохранён.
2. **Движение.** Шаг стартует; follower ведёт агента к `(10, 0.2, 0)` со скоростью ходьбы до 2 м/с.
3. **Середина.** Сценарий запоминает начальный квадрат 3D-дистанции $d_0^2 = 20^2 + 0.2^2 = 400.04$ и убирает
   InteractionPoint, когда $d^2 \le 0.25\,d_0^2$, то есть при $d \le 10.0005$ м — примерно через 5 с ходьбы
   ([[SC-REMOVE-TARGET]]).
4. **Инвалидация.** Следующий update: наблюдение даёт `goalAvailable = 0` и `atDestination = 0`
   (`requireInteractionPoint`); цель прежняя, шаг `RunningStep`, continuation `goalAvailable == true` нарушено →
   поиск → предусловие не выполнено → плана нет → отмена задачи (follower останавливает агента, горизонтальная
   скорость обнуляется) → `Failed`.
5. **Ожидание.** На каждом update: исполнения нет → поиск → плана нет → `Failed`. Instance жив.
6. **Возврат.** Через 5 с **реального** времени (`steady_clock`, не время симуляции) сценарий возвращает
   InteractionPoint. Update: `goalAvailable = 1` → план найден → `Ready`; следующий update стартует шаг.
7. **Продолжение.** `MoveToCapability` (без `sourceRadius`) строит маршрут из двух точек origin → goal; follower
   сразу целится в `points[1]` = цель, поэтому агент идёт от текущей позиции, а не возвращается в origin.

Подтверждение прибытия — в главе [13](13-steering.md) §6: для этой пары радиусов (0.4 и 0.4) и подъёма цели на 0.2
3D-подтверждение после плоского прибытия не гарантировано [[INF]].

## 6. Типичные ошибки, границы и проверка

- **«План есть, движения нет».** После установки плана шаг стартует на следующем update; после успеха шага —
  тоже. В отладке это один кадр с `ReadyToStartStep`.
- **Старт с недоступной целью.** Возвращает `false` без retained instance.
- **Смена цели без плана.** Старое исполнение продолжается без continuation-проверки.
- **Explicit Cancel и `Failed`.** Разные вещи: первый не возобновится сам.
- **Прямой `StartAI*` для агента с решением.** Задача решения будет заменена, решение воспримет это как провал
  и перепланирует, после чего снова заменит задачу [[INF]].
- **Нет backoff.** Без плана поиск идёт каждый update.
